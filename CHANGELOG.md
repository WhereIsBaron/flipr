# FLIPR Changelog

Patch notes for FLIPR, a bazaar-flip profit tracker userscript for Torn. Created by The_Baron [1467784] (MIT licensed).

---

## v2.4.1
- **Small:** **A "Make a FLIPR-only key" link** now sits next to the API key box. It opens Torn's Custom Key Builder with only the two things FLIPR reads already ticked: your own activity log, and the public item-name list. A key scoped that way cannot read your money, battle stats, messages or faction data, so a leak costs you far less than a Full key would. A Full key still works if you already use one.

## v2.3.0
- **Small:** **The panel now opens where you left the button.** Drag the collapsed "F" anywhere, click it, and the window appears in that same spot instead of jumping to a separately remembered one. Brought over from the private build, which has worked this way for a while.
- **Note:** these were kept as two separate positions to stop a button parked at the right edge opening the window off-screen on a phone. That can no longer happen for a different reason: the panel is re-fitted to the screen at its current size every time it opens, so a right-edge button now pulls the window fully back into view. Your old saved positions are kept, not wiped.

## v2.2.0
- **Moderate (new feature):** **Prices in Holdings can now be edited.** Click any price, type the right one, Enter to save (Escape cancels). It takes `4517899` or `$4,517,899`, so you can paste straight from Torn. Until now a mis-read price could only be deleted, which threw away the whole record along with the mistake, and a wrong cost quietly skews every profit figure that purchase ever feeds into.
- **Note:** with "Lump same items together" on, a row is an average across several purchases, so editing it sets them ALL to the price you enter. There is no way to split one number back across them honestly. Hovering the price says which mode you are in before you click.

## v2.1.1
- **Fix:** if you installed v2.1.0, an Item Market purchase could be logged twice. The new shop wording was checked too early and swallowed the seller's name into the item name ("Erotic DVD from Illuminescense"), so the API log's copy of the same purchase no longer matched it and got stored as a second lot. The shop wording now runs last, and only on shop pages, where there is no seller to swallow. Delete any Holdings row with a seller name stuck on the end; the correctly named row beside it is the real one.

## v2.1.0
- **Major (new feature):** FLIPR now logs **shop purchases** - both the foreign shops abroad and the city shops at home (asked for by a user who assumed it couldn't be done). Buy 28 plushies in Switzerland and they land in Holdings at what you actually paid, same as an Item Market or bazaar buy. Torn files both shop types under one log entry, so city and abroad arrive together.
- **Moderate (bug fix):** **Bazaar purchases could go missing from Holdings.** When the instant on-page read missed a bazaar buy, the API log was supposed to catch it - but it never could. Torn records a bazaar purchase differently to an Item Market one (the price sits on the purchase, not on each item), and FLIPR only knew the Item Market shape, so the price came out blank and the buy was dropped. It passed every other check first, which is why nothing looked wrong: no error, no warning, the purchase just wasn't there. Now handled.
- **Note:** this fixes purchases from here on and cannot back-fill old ones. If your Profits tab shows sales with "no cost basis", some of those are likely bazaar buys lost to this - they'll stay that way, but it stops growing.
- **Note:** city shop buys now appear in Holdings too, so routine supply shopping will show up alongside flip stock. Say so if you'd rather it tracked foreign shops only.

## v2.0.2
- **Points flips now count as profit.** Selling points was logged as "no cost basis", so a points flip showed the money coming in but no profit, and the purchase stayed in the Points tab forever. Points now work exactly like items: selling them matches against what you paid (oldest first), counts the profit in the Profits tab, and removes them from the Points tab. The tab is now "Points Held" rather than a lifetime purchase list.
- **Note:** this applies to points sold from now on. Points you sold *before* this update were already recorded without a cost basis and can't be back-filled - clear those leftover rows with the X if they are still listed.

## v2.0.1
- **FLIPR now works on the Torn PDA.** It never has - the panel just never appeared, no error, no clue. The cause was a few special characters in the script (the "x" in "3x Xanax", the separator dots, arrows, the gear icon, some curly apostrophes). The PDA garbles those when it stores a script, which broke the file badly enough that it refused to run at all. They are now written a different way. **The panel looks exactly the same.** Desktop is unaffected.
- **PDA users:** install this, then add it under Settings > User scripts. No API key to paste - the PDA supplies its own. (Multi-tab sync is the one desktop-only feature.)

## v2.0.0
- **Milestone: FLIPR now tracks what you made, not just what you paid.** The Profits tab (v1.2.0.59) and exact-copy matching for weapons and armor (v1.2.0.60) turn it into a full profit-and-loss tool. No behavior change from 1.2.0.60 - just the version number.

## v1.2.0.60
- **Moderate:** Sales now match to the **exact copy** you bought when possible, so profit on weapons and armor is correct even when you own two of the same item bought at different prices. Torn tags non-stackable items with a per-copy id; FLIPR now records it on purchase and uses it to pair a sale with the specific copy that sold, instead of always assuming the oldest one. Previously, selling the pricier of two identical-named weapons first would book the cheaper one's cost against it (overstating that sale's profit and leaving the wrong cost on the one still held) - and if you never sold the other, that error was permanent. Stackable items (drugs, materials, etc.) are unaffected: they're fungible, so oldest-first was already correct for them, and still applies. Existing holdings work as-is, no reset needed; the exact match kicks in for purchases logged from this version on.

## v1.2.0.59
- **Major (new feature):** A **Profits** tab. FLIPR now auto-logs your **sales** the same way it logs buys, and shows your **realized profit** over time (requested on the forums by RiotFrog [3643615]). When a listing sells, FLIPR matches it against what you paid for that item and records the profit, so the tab shows: total realized profit, how much you sold with a known cost, how much came from items you never bought through FLIPR (crime loot, stock you owned before installing - counted as sold but with no cost basis), and how much Item Market sales tax you've paid (which selling through your own bazaar avoids). Needs your API key set, since sales are read from your log. It tracks forward from this update, not retroactively.
- **Moderate:** Selling now **clears items from Holdings automatically**. Previously you cleared a holding by hand with the ✕ once it sold; now a detected sale reduces (oldest-first) the matching holding for you. The ✕ is still there for manual corrections. This is what lets the profit math stay exact.
- **Note:** the profit for weapons/armor is matched by item name and oldest-purchase-first, because a sale in your log doesn't say which specific rolled copy sold. For stackable flip items (the usual case) this is exact; for a stack of differently-rolled weapons it picks the oldest, which can misattribute which individual copy's cost was used, though the total across them stays right. "Clear profit history" (Profits tab) resets just the profit numbers and keeps your holdings and purchases.

## v1.2.0.57
- **Moderate:** A second pass at Torn PDA support, this time checked against BUSTR (which is confirmed working on the PDA) instead of guessed at. Two of the v1.2.0.56 assumptions were simply wrong, and one of them mattered:
  - **The likely reason you saw nothing at all.** FLIPR asked to be started at "document-idle". BUSTR asks for "document-end" and shows up fine, and the PDA's script engine is known to only handle the start/end options - so the most probable outcome is that FLIPR was never started on the PDA at all, which is exactly the "I can't see it anywhere" you reported. FLIPR now asks for "document-end" to match. Desktop is unaffected in practice (it just starts a moment earlier, and everything it touches on startup is now guarded).
  - **The storage fallback was pointed at the wrong path.** v1.2.0.56 fell back to browser storage only when Tampermonkey's storage was missing entirely. It turns out the PDA does provide those functions, as a shim that doesn't reliably keep anything between page loads - so FLIPR would have detected them, used them, and still forgotten your holdings on every page load. It now detects the PDA directly (via the key placeholder the PDA fills in) and forces browser storage there regardless. Desktop still uses Tampermonkey storage, so existing data loads exactly as before.
- **Small:** On the PDA, FLIPR now uses the API key the PDA app already injects, so there's nothing to paste in on mobile. A key you've saved yourself still takes priority, so nothing changes for an install that's already set up.
- **Small:** The debug export now reports which environment and storage path an install actually took (never the key itself, only yes/no plus the window size). A PDA report can be diagnosed from it directly rather than inferred.
- **Note:** still developed and tested on desktop only. The PDA changes are now modelled on a script confirmed to work there rather than on reasoning alone, but they remain unverified on a device - if FLIPR still doesn't appear, send the debug export (or say that you can't get one) and it can be narrowed down properly. One known PDA limitation remains: live sync between multiple tabs relies on a Tampermonkey-only feature, so it doesn't apply there (a single PDA webview doesn't need it).

## v1.2.0.56
- **Moderate:** Torn PDA compatibility (reported: FLIPR completely invisible on the PDA). Two separate problems, both fixed:
  - **It never appeared.** The PDA's script engine can start the script while the page is still loading, before the page body exists. Desktop is unchanged and keeps using Tampermonkey storage, so existing data loads exactly as before.
- **Note:** this is developed and tested on desktop only - the PDA fixes are based on how its script engine differs, and are not verified on a device. If FLIPR still does not show on your PDA, say so and include what you see. One known PDA limitation remains: live sync between multiple tabs relies on a Tampermonkey-only feature, so it does not apply there (a single PDA webview does not need it).

## v1.2.0.53
- **Moderate:** Closes the last hole in bazaar stat capture (reported after v1.2.0.52: a Lorcin 380 bought from a bazaar still saved blank). The v1.2.0.52 fix stopped a mismatched read only when the wrong card's stats failed the weapon range check. But if the neighbouring card is itself a valid weapon, its real stats pass - so a Lorcin 380 buy stashed the adjacent Diamond Bladed Knife's genuine Damage/Accuracy under that knife's name, overwriting the correct Lorcin value captured a moment earlier. Root cause both times: opening a bazaar buy-menu hides the clicked card's own stats, so the reader walks up into the row that holds all three cards. The reader now stops the instant it reaches an element containing more than one card (bazaar cards carry a stable test marker), so it can never read a neighbour's data at all; the value captured on the card click is kept. Item Market capture is untouched (its cards don't use that marker).

## v1.2.0.52
- **Moderate:** Fixes bazaar weapon/armor buys that logged with no stats even after v1.2.0.51 (reported: a Sawed-Off Shotgun captured fine, but a Katana and a Beretta M9 bought right after saved blank). Cause: on a bazaar, opening a card's buy-menu covers that card's own stats, so the follow-up "Buy"/"Yes" clicks made the stat reader walk up one level into the row that holds all three cards, and it then read the first Damage/Accuracy/Armor icons it found across the whole row - pairing one card's value with a neighbour's name (e.g. a Combat Boots armor rating stashed under the adjacent Steyr AUG). That wrong read overwrote the correct one captured a moment earlier when the card itself was clicked. Weapons happened to survive because their stats are sanity-checked against a reference range that rejects a mismatch, but armor has no such range, so the bad value stuck. The reader now refuses to read when the stat icons come from more than one card (each card has its own icon group), so it can't pair across cards; the correct value captured on the card click is kept. The first bazaar buy each session was usually fine; a second buy done quickly after was the one that got clobbered.

## v1.2.0.51
- **Moderate:** Weapon and armor stats now capture from **bazaars** too, not just the Item Market. Until now the stat capture only ran on the Item Market, so a weapon or armor bought from someone's bazaar logged with no stats (reported: a Hammer bought from a bazaar showing Dmg 18.19/Acc 55.42 on the card saved as blank). Two things differ on a bazaar: it shows each stat as its own little icon-and-number (Damage, Accuracy, Armor) rather than the Item Market's accessibility labels, and its buttons read "Buy: Hammer" / "Show info: Hammer" rather than "Buy item Hammer, $...". FLIPR now reads both styles - each stat value is still taken from its own element, so the run-together-number bug the v1.2.0.49 fix closed can't happen here either - and reads the item name from either button style. The after-tax chip stays Item-Market-only (a bazaar buy isn't taxed the same way). Weapons are still range-checked; armor is stored as-read. No change to how Item Market buys are captured.

## v1.2.0.50
- **Moderate:** Armor now records its Armor rating, the same way weapons record Damage/Accuracy. On the Item Market grid an armor piece shows a single "armor" figure (no Damage/Accuracy), so FLIPR reads that value off the card the moment you click Buy - by its accessibility label, the same run-together-proof method the v1.2.0.49 weapon fix uses - and takes the item's name from the card's own Buy/View buttons (armor has no reference-range table to identify it by, unlike weapons). The Armor value is then attached to the purchase and shown in Holdings (e.g. "Armor 20.21"), so two copies of the same armor at the same price stay distinct instead of being lumped together. Weapons are unchanged; a weapon card never carries an armor label and vice versa, so the two can't cross over. Note: armor has no reference range to validate against, so its captured value is stored as-read (weapons are still range-checked). One housekeeping detail: this adds Armor to the internal key that tells two holdings apart, so after updating do a "Reset all data" and re-test - old test rows carry the previous key format and won't merge with fresh identical buys otherwise.

## v1.2.0.49
- **Moderate:** Weapon stats (Damage/Accuracy) now actually capture on the Item Market. The v1.2.0.48 diagnostic caught it: the two numbers sit in adjacent spans on the card with nothing between them, so reading the card's combined text glued them into one number ("16.83" and "51.46" ran together as "16.8351.46"), which failed the "needs two separate decimals" check - so the capture found the right card but stored nothing. FLIPR now reads each stat from its own accessibility label ("16.83 damage points" / "51.46 accuracy points") instead of the run-together card text, so the two values can't merge; that label also names which stat is which, so Damage and Accuracy no longer depend on their on-card order. The old run-together text read stays as a fallback but only when it finds two cleanly separated decimals. This is the same class of glued-number bug that the v1.2.0.39/40 money fixes solved, now closed for stats too. Armor is still not covered (no reference ranges to validate against).

## v1.2.0.40
- **Moderate:** Fixed the remaining duplication (reported: item quantities creeping up over time at the correct price - e.g. a real 5x buy becoming 10x+, no garbage price this time). It's the same concatenation problem as v1.2.0.39, but in the one money figure that version didn't tighten: the TOTAL, in the routine that pulls the "You bought..." sentence out of the Item Market's big combined-text blob. When the banner re-rendered with a digit glued onto the total ("total of $283,620" + a neighboring "1" -> "$283,6201"), the extracted sentence changed each time, so the "already processed this confirmation" guard didn't recognize it - and because the quantity and unit price it actually stores come from the clean "at $X each" earlier in the sentence, the re-log merged into the existing lot and silently inflated its quantity. That total is now matched strictly like every other money figure, so a glued total either extracts identically (and is caught as a re-render) or doesn't extract at all (and is dropped). Verified against the exact reported case.

## v1.2.0.39
- **Moderate:** The real fix for the recurring phantom duplicate at roughly 10x the real price (confirmed via debug export: a real "2x Diesel @ $6,940" buy produced a bogus second lot of "2x Diesel @ $69,400.50"). The on-page "You bought..." banner sometimes re-renders inside a wider DOM node whose combined text glues the total to a neighboring digit ("total of $13,880" + a "1" from the next listing -> "$13,8801"), and the money pattern used to swallow that extra digit as a valid, higher total - a different fingerprint, so it logged as a new purchase. Torn always formats money with proper thousands separators, so a malformed group like "13,8801" (four digits after the comma) can only be that concatenation. FLIPR now matches every money figure strictly (proper thousands grouping, no trailing digit or comma allowed), so a corrupted total simply fails to match and no lot is created - the real purchase was already logged once from the clean text. This is the "log the purchase once and ignore everything the page does afterward" behavior, done at the parse level.
- **Small:** Removed redundant code. Dropped the leftover `isInline` parameter (no longer read by anything) and the old age-marker history-feed heuristic, which was fully superseded by the structural "is this text inside a history/feed container" DOM check plus the multiple-matches-in-one-mutation rejection.

## v1.2.0.38
- **Moderate:** Fixed the slow-burn duplication (reported with a debug export: one 5x Diesel purchase re-logged 18 times over ~44 minutes, merging into a 90x row). Torn's "You bought..." confirmation banner STAYS on the Item Market page, and it re-renders every couple of minutes as the live listings update around it - each re-render fires the same text as a fresh page change, and the previous guard only suppressed repeats for a few seconds. FLIPR now remembers every confirmation text it has already processed for as long as that text keeps appearing (each re-sighting refreshes the memory), so a persistent banner can never re-log no matter how long the page sits open. The one thing this can suppress is a genuine rebuy whose confirmation is byte-identical (same seller, same quantity, same price - the text contains all three); that purchase is still stored, exactly once, by the API poll within seconds.
- **Moderate:** Made the API poll actually reliable. It previously only fetched log entries newer than the last seen timestamp, which silently LOSES purchases on a busy account: Torn publishes log entries late (a points entry was observed arriving ~26s after the purchase), so any newer race/nerve/bust entry fetched in between pushed the cutoff past the purchase before it ever became visible - confirmed by debug exports showing the poll fetching 0 entries while real purchases sat in the log. The poll now re-fetches a rolling 15-minute window every time and skips what's already stored via the log-id ledger, so a late-published purchase is always picked up. This is also what makes the API a dependable backstop for the banner fix above, and it backfills purchases made shortly before a page reload.

## v1.2.0.37
- **Moderate:** Fixes two regressions from v1.2.0.36. (1) Purchases stopped recording. Making the on-page scan display-only in .36 meant every buy depended on the API poll alone, but a busy account's activity log is flooded with non-purchase entries (races, nerve, busts) that race the poll's watermark past a not-yet-published purchase entry, so it was never fetched - nothing got logged. (2) Points recording had become slow (~26s), waiting on that same laggy poll. Both are fixed by restoring the instant on-page scan as the primary writer (it stores the moment the confirmation appears, and it catches purchases the API poll never fetches), while keeping it dup-free with a rebuilt reconciliation: the on-page scan and the API poll now hand each other tickets in BOTH directions (whichever stores a purchase first leaves a ticket the other consumes and skips), and those tickets now live for 2.5 minutes instead of 20 seconds - comfortably longer than Torn's points-log publish lag, which was the real cause of the original double (the late poll's ticket had already expired). Net: instant recording again, and no duplicates.
- **Small:** The after-tax market chip is now scoped to real Item Market listings. It was firing on almost any click on the page (including the left info panel's "Money $X") because it only checked the page URL. It now only appears when the clicked element is an actual listing (has a buy/quantity/availability control) and never reacts to the left menu, header, chat, or FLIPR's own panel.

## v1.2.0.36
- **Moderate:** Definitive fix for purchases being logged twice (reported: every Points Market buy stored 2x - a 6-point buy became 12, a 30 became 60). Root cause: FLIPR had two independent writers for the same purchase (the instant on-page scan and the API log poll), and the reconciliation between them only worked when the on-page scan won the race. On the Points Market the API poll usually wins first, and the on-page scan then stored a second copy with nothing to tell it the purchase was already recorded. Fixed structurally by making sure there is only ever ONE writer: when you have a working API key, the API poll is the single source of truth (it is keyed on Torn's unique per-purchase log-entry id, so it can never double-count and it still records genuine rapid rebuys correctly), and the instant on-page scan becomes display-only - it just triggers an immediate poll so Holdings still update in about a second, but it no longer stores anything itself. Without an API key nothing changes: the on-page scan remains your sole writer. This also let the old cross-path "ticket" reconciliation machinery be removed entirely. If your points/holdings were already inflated by the old double-logging, use "Reset all data" and re-add - the affected totals can't be auto-corrected.

## v1.2.0.31
